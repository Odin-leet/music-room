# Defense: questions and answers

The questions an evaluator is likely to ask, in the order of the marking sheet, with short answers. Each one points to where to show it (code, test or document). The detailed explanations are in [`docs/technical/`](technical/README.md).

**How to use it:** read the answer, then **say it in your own words**, and open the file it points to. Evaluators trust what you can show more than what you recite.

Marks: ✅ = we do it · ⚠️ = partly / be ready to argue · ❌ = not done (say so honestly, with the reason).

## 0. Setting it up on the correction station

**"Show me how to install and start the solution."** ✅
- One command: `make start`. It checks Node ≥ 22.18 and Docker, creates the `.env` files (a random JWT secret), installs, starts Postgres and Mailpit, applies the migrations, then runs the API, the web app and Expo with its QR code.
- On Linux only Docker Engine + the Compose plugin are needed.
- Show: `scripts/setup.sh`, `scripts/start.sh`, [01-running.md](technical/01-running.md).

**"Where is the database initialisation?"** ✅
- The **migrations** in `apps/api/src/migrations/` (12 files, plain SQL generated by TypeORM and read before use). `make setup` applies them all.
- `synchronize` is off, so the schema only changes through migrations.

**"The Google keys aren't in the repo?"** ✅ on purpose
- Secrets never go in git (`.env` is ignored, `.env.example` has placeholders).
- We bring our `.env` for the defense. Without it, everything except Google / Facebook sign-in works.

## 1. Technical choices

### Storage

**"Why PostgreSQL?"** ✅
- Proven, open source, scales (indexes, connection pooling, read replicas).
- Above all, **transactions and constraints**: what must stay right under concurrency is guaranteed by the database, not by app code:
  - one vote per person per track: a primary key;
  - one playing track per event: a partial unique index;
  - strict playlist order: a unique position;
  - one friendship row per pair: a primary key + a CHECK.
- Show: [03-data-model.md](technical/03-data-model.md) → "The rules the database itself enforces".

**"Why not MongoDB / Firebase / Supabase?"**
- The data is relational: users ↔ memberships ↔ events / playlists ↔ tracks ↔ votes. The hard parts need multi-row transactions and unique constraints.
- The brief says the SDK must not do the work. A backend-as-a-service would hide exactly what's graded: auth, access rules, realtime, concurrency.

**"How would it scale?"**
- More API processes behind a load balancer: the API is stateless (JWT), except in-memory rate limits and socket rooms, which would move to Redis.
- Postgres: bigger machine, pool, read replicas.
- These limits are written down in [security.md](security.md) (accepted risks) and in [loadtests/README.md](../loadtests/README.md) (§4).

### Server

**"Why NestJS?"** ✅
- Proven Node framework: modules, dependency injection, guards, pipes, interceptors.
- Every rule applies to every route in one place: validation, auth, rate limits, the action log.
- TypeScript end to end, sharing its types with the apps (`packages/shared`).
- Socket.IO gateways for realtime.

**"Why Socket.IO and not polling?"**
- Updates arrive instantly with no wasted requests.
- Rooms per event / playlist / user; automatic reconnection.
- The socket only **sends news**: every change still goes through REST, so it's validated, authorised and logged once.

### Securing the back end

**"Who can access the database?"** ✅
- Only the API and an admin tool. Postgres listens on **127.0.0.1 only** (`docker-compose.yml`), so nothing on the network can reach it.
- Admin tool: `make db-shell` (psql inside the container).

**"Is the API the only entry point?"** ✅
- Yes: the apps only talk to the REST API and its sockets. Deezer, Google and Facebook are called **by the server**, never by the apps.
- Mailpit's inbox is also on 127.0.0.1, and it's dev only.

**"How do you control what's sent to the API?"** ✅
1. **Validation** on every body and parameter (class-validator DTOs), with `whitelist` + `forbidNonWhitelisted`: any field a route doesn't declare is a 400. So nobody can send `ownerId`, `score` or `emailVerifiedAt`.
2. **Authentication**: a JWT on every protected route and socket.
3. **Authorisation** by policy functions on every route, with someone else's ids tested: `test:idor`, 57 attacks.
4. **Rate limits**:
   - 300 / min per user;
   - 10 auth attempts / min per IP + email;
   - 100 / min per IP;
   - plus a lockout after 5 wrong passwords.
5. **Server-side data**: track details are fetched from Deezer by the server, never trusted from the app.
6. **CORS** allows only the web app's origins.
7. **An action log**: one JSON line per action, with platform / device / version.

Show: [security.md](security.md) (threats → protections → tests), `npm run test:idor --workspace=apps/api`.

**"What happens if someone steals a token?"**
- **Access token:** 15 minutes, then useless.
- **Refresh token:** stored hashed and rotated on every use. If an old one is reused, **every session of that user is revoked** (theft detection). A password reset also ends every session.

### Back-end support (load)

**"Did you measure how many users the server holds?"** ✅
- k6, on a stated machine (MacBook Pro 2019, i7 6 cores, 16 GB, one Node process, Postgres in Docker), with realistic users: 80% voting at a party, 20% editing a playlist, each with its own socket.
- **About 200 concurrent users** with every limit met: REST p95 < 300 ms, a vote reaching the other phones p95 < 500 ms, < 1% errors.
- **No request ever failed and no data was ever corrupted, even at 800.** Over the limit it gets slower, it doesn't break, and it recovers at once after a 500-user spike.
- Read it as a **lower bound**: k6 ran on the same laptop and took up to half the CPU.
- Show: [loadtests/README.md](../loadtests/README.md), `make load-test`.

**"What limits it, and what would you change?"**
- Each vote broadcasts the whole queue (~11.5 KB) to every phone at the party, and there's one Node process (one core).
- Fixes: send Track Vote **changes** instead of the full queue (as the Playlist Editor already does), a Node cluster + the Socket.IO Redis adapter, a separate load-generator machine.

## 2. The API

**"REST? JSON?"** ✅
- REST over HTTP with JSON bodies, plus Socket.IO for server → client news.
- Status codes are used as meant:
  - 201 created, 204 no content;
  - 400 invalid, 401 not logged in, 403 not allowed, 404 not found or hidden, 409 conflict;
  - 429 too many requests.

**"Are the routes consistent?"** ✅
- Resources in the plural, nested by ownership: `/events/:id/tracks/:trackId/vote`, `/playlists/:id/tracks/:trackId`, `/friends/requests/:userId/accept`.
- The same shapes for events and playlists: `join`, `join` by code, `invites`.
- **One error shape** everywhere: `{ statusCode, message, error }`. Validation errors are one message per field, and refusals carry a `reason` the app can explain.
- **The same rule gives the same answer:** something private you're not in answers **404** (its existence isn't revealed), never 403.

**"Where's the documentation?"** ✅
- **http://localhost:3000/api-docs** (Swagger UI): every route with its full request / response schemas, examples, auth (Authorize button), rate limits and every error.
- The same as a file: `docs/openapi.json`.
- The realtime messages are documented in `docs/realtime.md`, linked from the Swagger description.

## 3. The mobile app

**"Which framework, which patterns?"** ✅
- React Native with **Expo SDK 57** and expo-router: file-based routes, one codebase for Android and iOS.
- Patterns:
  - **providers** for app-wide state: session, current user, the `/me` socket, the player;
  - **hooks** for each live feature;
  - a small **UI kit** on one theme file;
  - **shared types** with the API.
- The app holds no business rule: the server decides, the app displays.
- Show: [08-apps.md](technical/08-apps.md).

**"Did you integrate Facebook / Google SDKs?"** ✅ (be ready to explain the "how")
- Users can **sign in** with Google and Facebook, and **link** either one to an existing account (or unlink it) from their profile.
- We use the providers' **official OAuth 2.0 / OpenID Connect flows**: Google's `google-auth-library` on the server verifies the ID token; Facebook uses its Graph API with `appsecret_proof`. We don't use the native SDKs inside the app.
- **Why:** the client secret stays on the server, and the app only ever receives a single-use 60-second code, protected by PKCE. It also works the same in Expo Go, our own builds and the web app.
- Show: [04-auth.md](technical/04-auth.md) → "Google and Facebook sign-in", "Linking", `npm run test:links --workspace=apps/api`.

**"Did you integrate the Deezer API / SDK, so users can connect their Deezer account?"** ⚠️ / ❌ for the account part
- **What we do:**
  - all music comes from **Deezer's API**: search, track details, 30-second previews;
  - it's called by our server, which fetches a fresh preview link before each track (they expire after about 15 minutes) and skips tracks with no preview.
- **What we don't do:** connecting a user's own Deezer account (Deezer OAuth: their playlists, full tracks).
- **Why, said honestly:**
  - full-length streaming needs Deezer's native SDK and a registered Deezer app, and Deezer's developer platform no longer accepts new app registrations (**check the current state on developers.deezer.com before the defense**);
  - the public API needs no account and covers what both services need: search, metadata, previews.
- **Possible next step:** linking a Deezer profile by its id and importing its **public** playlists through the public API.

**"Can the user manage their account: personal info, preferences, friends, playlists, devices, access rights?"** ⚠️
- ✅ **Personal information:** display name, bio, real name, city, phone, birth date, each in its visibility tier (public / friends / private).
- ✅ **Preferences and settings:** music genres and favourite artists with their own visibility; the server address (Server settings); the sign-in methods (password, Google, Facebook: link / unlink).
- ✅ **Friends:** search, requests, accept / decline, unfriend, live.
- ✅ **Playlists and events:** create, settings (visibility, who can edit / vote), invite by email, invite code, delete.
- ⚠️ **Devices:**
  - each device signs in separately and gets its own session (refresh token);
  - every request and socket carries the device's platform, model and app version, which go into the action log;
  - signing out ends that device's session, and a password reset ends them all.
  - **Not built: a screen listing your devices** to sign one out remotely.
- ⚠️ **Access rights:** the owner chooses who can see and who can vote / edit, invites people by email (they get the right immediately, live), and can turn an event private (people without access are removed from it live). **Not built: a list of members to remove one person.**

**"Did you test it with people outside the project?"**
- Show [user-testing.md](user-testing.md): who tested, what they said, what changed.
- Also mention what we changed from using it ourselves (§6 there).

## 4. Feature 1: Music Track Vote ✅

**"Show several people voting."** Two phones (or a phone + the web app) in the same party. A vote on one reorders the queue on the other within about 200 ms.

**"Does the most-voted song play first?"**
- Yes: most votes first.
- At equal votes, the **earliest suggestion** goes first, so tied songs never swap places. That's our tie-break rule, and it's unit-tested (`ranking.spec.ts`) and checked against the real queue (`test:race`, section E).

**"How do you handle concurrency?"** ← the key question
- **One vote per person:** the primary key `(track, user)` on `votes`. 10 identical votes at once → one row.
- **The score:**
  - it changes with `score = score + 1` **inside** the database, in the same transaction as the vote row;
  - Postgres applies concurrent increments one after another;
  - no read-then-write in the app, so no lost vote.
- **Proof:** `test:race`. 10 users voting at the same instant give **exactly** 10; the same vote sent 10 times at once counts once.
- **Playback:** Next locks the event row (`FOR UPDATE`) and carries the track the device thinks is playing, so a double tap can't skip two songs. A unique index allows only one playing track.

**"Visibility: public / private?"**
- **Public:** listed for everyone.
- **Private:** visible to members only. You become a member when the owner invites you by email, or with the invite code. Others get 404.

**"Voting rights: everyone / invited / place + time slot?"** All three:

| License | Who votes |
|---|---|
| Everyone | anyone who can see the event |
| Invited only | accounts the owner invited by email. The invite code lets you watch, not vote |
| On site, on time | inside a radius around the owner's position, between a start and an end time |

- The geo check uses the distance (haversine) from the location the phone sends.
- **"Can't someone fake their GPS?"** Yes, a rooted phone can. The server checks, **logs every geo decision** and rate-limits. It's a listed accepted risk: reliable fake-GPS detection isn't possible from an app.

**"Who plays the music?"**
- **The owner's device is the speaker:** it plays each 30-second preview and moves the queue on at the end.
- Everyone sees "Now playing" live.

## 5. Feature 2: Music Playlist Editor ✅

**"Several people editing at the same time?"** Two devices on the same playlist: add, remove, reorder. Every change appears on the other within moments, with no lock and no waiting.

**"How do you keep the order right when two people move tracks at once?"** ← the key question
- **Fractional positions.** Each track's position is a sortable string key. Moving a track gives it a key **between its two new neighbours**, and no other row changes.
- Two people moving different tracks touch different rows: nothing to lock, nothing lost.
- The rare collision (same gap, same instant, same key) is caught by a **unique index**; the server re-reads the neighbours and retries at a random spot in the gap.
- **Proof:**
  - `test:playlist-race`: 10 simultaneous moves, 10 inserts into one gap, the same track moved two ways at once;
  - `test:playlist-realtime`: 30 concurrent edits, and every device ends with exactly the server's list.
- Show: [07-playlist-editor.md](technical/07-playlist-editor.md).

**"Can it be listened to while it's being modified?"**
- Yes. The player continues in the playlist's **current** order: at the end of each track it re-reads the playlist, so others' moves and removals are respected.

**"Visibility and editing rights?"**
- Visibility: **public / private** (as for events).
- Editing: **anyone who can see it**, or **invited only** (everyone else can only listen). The owner changes both at any time, live.

## 6. Music Control Delegation ❌ (not built: the brief asks for 2 of the 3)

**"Why not this one?"**
- Track Vote and the Playlist Editor carry the hard problems (concurrency, realtime, rights). Delegation would mostly repeat them.
- Its real cost is on the device side: a phone obeying remote commands reliably in the background needs a development build, not Expo Go.
- The design is written: [control-delegation.md](control-delegation.md). It covers device-scoped licences, the grant / revoke model and the routes.

## 7. Questions that often come up anyway

**"What if Deezer is down?"** Search and previews answer 502 "Music provider unreachable" (8-second timeout). Everything else keeps working: queues, votes, playlists, accounts.

**"What if two people register the same email at the same time?"** The database's unique constraint lets one win; the other gets 409. Emails are stored lower-case (a CHECK constraint), so `Bob@x.com` and `bob@x.com` are the same account.

**"How are passwords stored?"** bcrypt, cost 12. Login takes the same time for unknown emails (a dummy hash), so it doesn't reveal which emails exist.

**"Why both a mobile app and a web app?"** The brief asks for mobile. The web app is a bonus on the same API: it proves the API is a real, documented, client-independent interface.

**"What do you log?"**
- One JSON line per action: route, status, duration, user, IP, platform / device / app version.
- Never bodies, tokens or query strings.
- Show it live: `make logs`.

**"What's tested automatically?"**
- 67 unit tests: access rules, positions, ranking, PKCE, allowed return addresses.
- 9 scripts against a real API and Postgres: concurrency, realtime, linking, IDOR, rate limits.
- GitHub Actions runs all of it on every push.
- Show the CI badge in the README and a green run.

**"What would you do with more time?"**
1. A devices screen and member management.
2. Track Vote broadcasting changes instead of the whole queue.
3. Redis for several API instances.
4. Deezer profile linking.
5. Control Delegation.
